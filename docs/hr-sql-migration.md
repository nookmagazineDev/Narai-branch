# ย้ายตารางงานจาก Google Sheets ไปฐานข้อมูล

ข้อมูลส่วน "ลงตารางงาน" ย้ายจาก Google Apps Script + Google Sheets มาเก็บใน
**MySQL** เครื่อง **inventory.dyndns.tv** ฐานข้อมูล **narai_hr**
(เครื่องเดียวกับฐานข้อมูล `myfbdata` ของระบบสต๊อก)

> **เคยอยู่บน MS SQL Server** เครื่องเดียวกันมาก่อน แล้วย้ายมา MySQL ทีหลัง
> เพื่อให้เหลือฐานข้อมูลเดียวที่ต้องดูแล/เปิดพอร์ต/สำรองข้อมูล
> วิธีย้ายอยู่ที่หัวข้อ [ย้ายจาก SQL Server มา MySQL](#ย้ายจาก-sql-server-มา-mysql)
> ส่วนของเดิมยังเก็บไว้ดูได้ที่ `docs/schema-hr.sql` (เลิกใช้แล้ว)

หน้าเว็บไม่ได้แก้อะไรเลย — `src/services/api.js` เป็นตัวตัดสินว่า action ไหนวิ่งไป SQL
action ไหนยังวิ่งไปชีท (ดูตัวแปร `SQL_ACTIONS`) จึงย้ายทีละกลุ่มได้โดยไม่ต้องหยุดใช้งานระบบ

```
เบราว์เซอร์ ──apiCall(action)──┬─ action อยู่ใน SQL_ACTIONS ─→ /api/schedule ─→ MySQL inventory.dyndns.tv
                               └─ นอกนั้น ────────────────────→ Google Apps Script (ชีทเดิม)
```

## การล็อกอิน — ใช้ user เดิม ไม่ล็อกอินซ้อน

ฝั่ง SQL **ไม่มีการล็อกอินอีกชั้น** ผู้ใช้ล็อกอินครั้งเดียวที่หน้าเดิม (ยังผ่าน Apps Script)
แล้ว `AuthContext` เก็บ user ไว้ที่ `localStorage['hr_user']`

จากนั้น `apiCall()` จะแนบ user คนนั้นไปกับทุกคำสั่งที่วิ่งไป SQL ให้เองในฟิลด์ `_user`
หน้าเว็บไม่ต้องส่งชื่อผู้ใช้/ชื่อผู้อนุมัติเองอีกต่อไป ฝั่ง `/api/schedule` เอาไปใช้ 3 อย่าง

| ใช้ทำอะไร | เดิม | ตอนนี้ |
|---|---|---|
| คนที่กดบันทึก (`updated_by`, `hr_timesheet_log.actor`) | ไม่ได้เก็บ | มาจาก user ที่ล็อกอินไว้ |
| ชื่อผู้อนุมัติ OT | หน้าเว็บส่ง `approverName` มาเอง | มาจาก user ที่ล็อกอินไว้ (ปลอมจากหน้าเว็บไม่ได้) |
| จำกัดสาขา | หน้าเว็บล็อกอย่างเดียว | เซิร์ฟเวอร์บังคับอีกชั้น — ไม่ใช่สิทธิ์ `all` เห็นได้แค่สาขาตัวเอง |

ถ้า `_user` หายไป (ล้าง localStorage หรือยังไม่ได้ล็อกอิน) endpoint ตอบ 401
พร้อมข้อความ "เซสชันหมดอายุ กรุณาเข้าสู่ระบบใหม่"

> **ข้อจำกัดที่ต้องรู้:** `_user` มาจาก localStorage ของเบราว์เซอร์ ซึ่งผู้ใช้แก้เองได้
> การจำกัดสาขาตรงนี้จึงกันการกดผิดสาขาโดยไม่ตั้งใจได้ แต่กันคนที่ตั้งใจปลอมไม่ได้
> (Apps Script เดิมก็เชื่อสาขาที่ฝั่งเว็บส่งมาแบบเดียวกัน จึงไม่ได้แย่ลงกว่าเดิม)
> ถ้าต้องการกันจริง ต้องให้ตอน login ออก token ที่เซ็นชื่อไว้ แล้วตรวจ token ที่ `/api/schedule`

## ขั้นตอนติดตั้ง

### 1. เปิดทางให้ต่อฐานข้อมูลได้

MySQL เครื่องนี้เปิดให้ระบบสต๊อก (`myfbdata`) ต่อจากอินเทอร์เน็ตอยู่แล้ว
พอร์ต **3306** จึง forward ไว้แล้ว ไม่ต้องทำอะไรเพิ่ม — เหลือแค่ให้ user
ที่จะใช้ต่อได้จาก host ภายนอก (`'narai_web'@'%'` ไม่ใช่ `@'localhost'`)

> ถ้าไม่อยากเปิดพอร์ตออกเน็ต ทางเลือกคือให้ `office-server` เป็นตัวกลางแทน
> (เหมือนที่ทำกับ ZKBio9 อยู่แล้ว) แล้วให้ `/api/schedule` proxy ไปที่นั่น

### 2. สร้างตาราง

```cmd
mysql -u root -p < docs\schema-hr-mysql.sql
```

แล้วสร้าง user แยกสำหรับเว็บ (อย่าใช้ `root`) ตามคำสั่งท้ายไฟล์ `schema-hr-mysql.sql`

### 3. ตั้ง environment variables บน Vercel

| ตัวแปร | ค่า |
|---|---|
| `HR_DB_HOST` | `inventory.dyndns.tv` (ค่าเริ่มต้นในโค้ดอยู่แล้ว) |
| `HR_DB_PORT` | `3306` |
| `HR_DB_NAME` | `narai_hr` |
| `HR_DB_USER` | user ที่สร้างไว้ เช่น `narai_web` |
| `HR_DB_PASSWORD` | รหัสผ่านของ user นั้น |

ถ้าไม่ตั้ง `HR_DB_USER`/`HR_DB_PASSWORD` จะถอยไปใช้ `MYSQL_USER`/`MYSQL_PASSWORD`
ที่ตั้งไว้ให้ `myfbdata` อยู่แล้ว (เครื่องเดียวกัน user เดียวกันมักใช้ได้เลย)
ถ้าไม่มีทั้งคู่ endpoint จะตอบ 503 พร้อมบอกว่ายังไม่ได้ตั้งค่า แทนที่จะค้างรอจนหมดเวลา

> **ตัวแปรที่ต้องลบทิ้ง** หลังย้ายมา MySQL: `HR_DB_INSTANCE`, `HR_DB_USE_BROWSER`,
> `HR_DB_ENCRYPT` (เป็นของ SQL Server ล้วนๆ) และอย่าลืมแก้ `HR_DB_PORT` จาก
> `1433` เป็น `3306` — ถ้าลืม โค้ดจะเตือนใน log แล้วใช้ 3306 ให้เอง

### 4. ย้ายข้อมูลเก่า

ชีท 2 ไฟล์ต้องตั้งลิงก์เป็น **"ผู้ที่มีลิงก์ • ผู้อ่าน"** ก่อน
(สคริปต์อ่านผ่าน gviz แบบไม่ล็อกอิน ถ้าชีทปิดอยู่จะได้หน้า login กลับมาแทนข้อมูล)

| ชีท | ไอดี |
|---|---|
| พนักงาน | `1Abot2hKLUO6_z8NRW6c9A0m0ggra3ZE7Yq10kcUPr7Y` |
| ลงตารางงาน | `1bGSENQjSmmYv8V84aInyqk-K7r4niSXFlPqv0zEFQ1U` |

```bash
export HR_DB_USER=narai_web HR_DB_PASSWORD='...'

# ดูก่อนว่าจะย้ายกี่แถว และจับคอลัมน์ถูกไหม ยังไม่เขียนจริง
node scripts/migrate-schedule.mjs --months=6 --dry-run

# ย้ายจริง
node scripts/migrate-schedule.mjs --months=6
```

สคริปต์ย้าย 2 ชุด: พนักงาน (สร้างรายชื่อสาขาให้ด้วย) → ตารางงาน
รันซ้ำได้ (เขียนทับตามคีย์ ไม่เกิดแถวซ้ำ) เลือกเฉพาะบางชุดด้วย `--only=timesheet` ได้

**ชีทพนักงานจับคอลัมน์จากชื่อหัวตาราง ไม่ใช่ตำแหน่ง** เพราะไฟล์ถูกย้ายมาแล้วครั้งหนึ่ง
(ไม่ใช่ไฟล์เดียวกับที่ Apps Script เดิมชี้ไว้) ตำแหน่งคอลัมน์จึงเชื่อไม่ได้
`--dry-run` จะพิมพ์ออกมาว่าจับได้คอลัมน์ไหน — **ต้องตรวจให้ตรงทุกช่องก่อนย้ายจริงเสมอ**

```
  hrCode      <- C "รหัสพนักงาน"
  branch      <- E "สาขา"
  name        <- D "ชื่อ-สกุล"
  ...
```

ถ้าบรรทัดไหนขึ้นว่า `(ไม่พบหัวคอลัมน์ ใช้ตำแหน่งเดิม)` แปลว่าเดาไม่ออก
ต้องไปแก้ `EMP_COLUMNS` ในสคริปต์ให้ตรงกับหัวตารางจริงก่อน

### เป้าขาย / ค่าแรงสูงสุด / ยอดขายรายวัน

ชีท `Details` และ `ยอดขายสาขา` เลิกใช้แล้ว จึงไม่มีการย้ายเข้า SQL
ผลคือการ์ดบนหน้าลงตารางจะขึ้น 0 จนกว่าจะกรอกเป้าลงตาราง `hr_branch` เอง

```sql
UPDATE hr_branch SET daily_target = 40000, max_wage = 6000 WHERE branch = '<รหัสสาขา>';
```

ส่วน "ยอดขายของวัน" ในหน้าประวัติจะเป็น 0 เสมอจนกว่าจะมีแหล่งข้อมูลใหม่
(ระบบมี `/api/dashboard` ที่ดึงยอดขายจริงจาก POS อยู่แล้ว ต่อเข้ามาแทนได้ถ้าต้องการ)

## ย้ายจาก SQL Server มา MySQL

ทำครั้งเดียวตอนเลิกใช้ SQL Server ใช้ `scripts/mssql-to-mysql.mjs` คัดลอกทั้ง 5 ตาราง
(`hr_branch`, `hr_employee`, `hr_timesheet`, `hr_timesheet_log`, `hr_daily_sales`)
สคริปต์อ่านอย่างเดียวจากฝั่ง SQL Server ไม่ได้ลบหรือแก้อะไรที่ต้นทางเลย
ของเดิมจึงยังอยู่ครบไว้ย้อนกลับได้ถ้าจำเป็น

รันบนเครื่องที่ต่อได้ทั้งสองฝั่ง (ปกติคือเครื่องที่ออฟฟิศ)

```cmd
mkdir C:\hr-migrate && cd C:\hr-migrate
npm init -y && npm i mssql mysql2
:: วางไฟล์ scripts\mssql-to-mysql.mjs ไว้ในโฟลเดอร์นี้

:: 1) นับแถวก่อน ยังไม่เขียนอะไร (ไม่ต้องมี MySQL ก็รันได้)
node mssql-to-mysql.mjs --dry-run --src-host localhost --src-user narai_web --src-pass "<รหัสผ่าน>"

:: 2) ย้ายจริง — สร้างฐานข้อมูล/ตารางฝั่ง MySQL ให้เองถ้ายังไม่มี
node mssql-to-mysql.mjs --src-host localhost --src-user narai_web --src-pass "<รหัสผ่าน>" --dst-pass "<รหัสผ่าน root>"
```

จบแล้วสคริปต์จะนับแถวฝั่งปลายทางให้ดูว่าตรงกับต้นทางไหม
รันซ้ำได้เรื่อยๆ (เขียนทับตามคีย์) จึงย้ายล่วงหน้าไว้ก่อนแล้วค่อยรันซ้ำตอนจะสลับจริงได้
ถ้าอยากให้ปลายทางเหมือนต้นทางเป๊ะๆ (ลบของที่ต้นทางลบไปแล้วด้วย) ใส่ `--truncate`

**ลำดับที่ปลอดภัยตอนสลับจริง**

1. รัน `--dry-run` ดูจำนวนแถว
2. ย้ายจริง แล้วดูว่ายอดตรงกัน
3. แก้ env บน Vercel (`HR_DB_PORT` = 3306, ลบ `HR_DB_INSTANCE`/`HR_DB_ENCRYPT`,
   ตั้ง `HR_DB_USER`/`HR_DB_PASSWORD` เป็น user ของ MySQL)
4. deploy แล้วเรียก action `ping` เช็คว่าต่อติด (`readMs`/`txMs` ต้องมีค่า)
5. รัน `--truncate` อีกรอบถ้ามีคนกรอกตารางเพิ่มระหว่างทาง — หรือปิดการใช้งานช่วงสลับ

## สิ่งที่เปลี่ยนไปจากของเดิม

**ชีทเดิมเป็น log ต่อท้ายอย่างเดียว** — กดบันทึกวันเดิมซ้ำก็ได้แถวใหม่เรื่อยๆ
แล้วตอนอ่านค่อยหยิบแถวล่าสุดมาใช้ ชีทจึงบวมและอ่านช้าลงทุกสัปดาห์

ใน SQL เก็บ **หนึ่งแถวต่อพนักงานต่อวัน** (PK = `work_date` + `branch` + `hr_code`)

| การกระทำ | ชีทเดิม | SQL |
|---|---|---|
| บันทึกซ้ำวันเดิม | ต่อท้ายแถวใหม่ | `INSERT ... ON DUPLICATE KEY UPDATE` ทับแถวเดิม |
| ล้างข้อมูลของวัน | ต่อท้ายแถวที่เขียนว่า `ล้างข้อมูล` | `DELETE` แถวนั้นจริง |
| ประวัติว่าใครแก้เมื่อไหร่ | ดูจากแถวเก่าที่ทับถมกัน | ตาราง `hr_timesheet_log` แยกต่างหาก (เก็บ actor + payload) |
| อนุมัติ OT | จับคู่ด้วย "ชื่อ" | จับคู่ด้วย `hr_code` (ชื่อซ้ำกันไม่โดนอนุมัติพร้อมกัน) |

เวลาเข้า/ออกเก็บเป็นข้อความ `HH:mm` ไม่ใช่ชนิด `TIME`
เพราะระบบเดิมใช้ค่า `24:00` ได้จริง (กะที่จบเที่ยงคืนพอดี) ซึ่ง `TIME` เก็บไม่ได้

## ข้อจำกัดของ Vercel ที่ต้องรู้

แผนที่ใช้อยู่จำกัด **12 Serverless Functions** และเต็มพอดีอยู่แล้ว
การเพิ่ม `api/schedule.js` จึงต้องยุบ `api/usagebytable.js` เข้าไปเป็นโหมดหนึ่ง
ของ `api/usagemenu.js` (`?bytable=1`) ก่อน — เหมือนที่ `api/dashboard.js`
รวมหลายโหมดไว้ในไฟล์เดียวอยู่แล้ว

**ถ้าจะย้าย action กลุ่มอื่นเพิ่ม ให้เพิ่มเป็น action ใน `api/schedule.js`
หรือไฟล์ที่มีอยู่แล้ว อย่าสร้างไฟล์ใหม่ใน `api/`** เพราะจะเกินลิมิตทันที

## รายชื่อพนักงาน — ชีทเป็นตัวหลัก SQL คัดลอกตามอัตโนมัติ

`getScheduleEmployees` **ไม่ได้ย้ายไป SQL** และจะไม่ย้าย — เพิ่มพนักงาน ให้ลาออก
แก้ค่าแรง ยังทำที่หน้ารายชื่อพนักงานเหมือนเดิมทุกอย่าง (ปลายทางคือ Google Sheet)

แต่ทุกครั้งที่หน้าไหนดึงรายชื่อพนักงานสำเร็จ `apiCall()` จะส่งรายชื่อนั้นไปเก็บใน
`hr_employee` ให้ด้วย (action `syncEmployees` ยิงแบบไม่รอผล ไม่กระทบเวลาโหลดหน้า)

```
หน้ารายชื่อพนักงาน ──เพิ่ม/ลาออก/แก้ค่าแรง──→ Google Sheet  (ตัวหลัก)
                                                    │
เปิดหน้าลงตาราง/นับสต๊อก ──getScheduleEmployees──────┘
                                    │
                                    └──syncEmployees──→ hr_employee (คัดลอกตาม)
```

ฝั่ง SQL ปรับตามให้เอง: คนใหม่เพิ่มเข้ามา, คนที่หายไปจากรายชื่อตั้งเป็น `ลาออก`
(ไม่ลบแถว เพราะกะเก่ายังอ้างอิง `hr_code` อยู่)

**เหตุผลที่สำคัญกว่าความสะดวก:** วิธีนี้ทำให้ SQL ได้ "รหัสพนักงานชุดเดียวกับที่
หน้าเว็บใช้" เป๊ะ ไม่ต้องเดาว่ารหัสในชีท HR (`0808001`) กับในตารางงาน (`740808001`)
ตัวไหนถูก ซึ่งเป็นปัญหาที่ทำให้ตอนย้ายข้อมูลครั้งแรกกะ 72% หาเจ้าของไม่เจอ

**กันพลาดไว้แล้ว:** ถ้ารายชื่อที่ส่งมาน้อยกว่าครึ่งของจำนวนคนที่ยังทำงานอยู่ใน SQL
จะไม่ตั้งใครเป็นลาออกเลย เพราะกรณีนั้นน่าจะเป็นชีทตอบมาไม่ครบ ไม่ใช่คนลาออกยกสาขา

`getBranches` ยังวิ่งไปชีทอยู่ ทั้งที่ `/api/schedule` รองรับแล้ว
เพราะมีอีก 7 หน้าที่ไม่เกี่ยวกับตารางงานใช้ action นี้ (บางหน้าอ่าน `outletId` ด้วย)
จะย้ายพร้อมกลุ่มของหน้าเหล่านั้นทีเดียว จะได้ทดสอบพร้อมกัน —
เมื่อพร้อมแล้วแค่เพิ่มชื่อ action ลงใน `SQL_ACTIONS`

action ที่เหลือของระบบ (สต๊อก, ของเสีย, รับของ, ค่าใช้จ่าย, ปิดรอบสิ้นเดือน,
พนักงาน, login) ยังอยู่บน Apps Script ทั้งหมด — ดูหัวข้อถัดไป

## ย้ายส่วนที่เหลือต่อ

ต้องใช้ซอร์ส Apps Script ของแต่ละส่วนก่อนถึงจะย้ายได้ เพราะต้องรู้ว่าชีทไหน
คอลัมน์ไหน และมีกติกาการคำนวณอะไรซ่อนอยู่ ในรีโปตอนนี้มีแค่ซอร์สของส่วนตารางงาน
(`indexลงตารางงาน.txt`) ซึ่งเป็นเหตุผลที่ย้ายส่วนนี้ได้ครบก่อน

ลำดับที่แนะนำ

1. **พนักงาน** (`getEmployees`, `addEmployee`, `resignEmployee`, `getNextHrCode`,
   `updateEmployeeLoga`, `uploadEmployeePhoto`) — ตาราง `hr_employee` มีอยู่แล้ว
   เหลือแค่ทำ action เพิ่ม รูปพนักงานต้องตัดสินใจว่าจะเก็บที่ไหน (ตอนนี้อยู่บน Drive)
2. **สาขา** (`getBranches`) — ย้ายพร้อมข้อ 1 แล้วทดสอบทั้ง 7 หน้าที่ใช้
3. **สต๊อก / ของเสีย / รับของ / ค่าใช้จ่าย / ปิดรอบสิ้นเดือน** — กลุ่มใหญ่สุด
   แต่ละอันมีชีทของตัวเอง แยกทำทีละอันได้

**login ไม่ต้องย้าย** — ผู้ใช้ล็อกอินครั้งเดียวที่เดิม แล้วฝั่ง SQL ใช้ user คนนั้นต่อ
(ดูหัวข้อ "การล็อกอิน" ด้านบน) ถ้าจะย้ายในอนาคตค่อยทำพร้อมกับเปลี่ยนรหัสผ่าน
จากข้อความล้วนในชีทเป็น hash และออก token ให้ตรวจสิทธิ์ได้จริง
