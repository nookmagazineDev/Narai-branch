# ย้ายตารางงานจาก Google Sheets ไป SQL Server

ข้อมูลส่วน "ลงตารางงาน" ย้ายจาก Google Apps Script + Google Sheets มาเก็บใน
Microsoft SQL Server เครื่อง **203.154.185.48** ฐานข้อมูล **narai_hr**

หน้าเว็บไม่ได้แก้อะไรเลย — `src/services/api.js` เป็นตัวตัดสินว่า action ไหนวิ่งไป SQL
action ไหนยังวิ่งไปชีท (ดูตัวแปร `SQL_ACTIONS`) จึงย้ายทีละกลุ่มได้โดยไม่ต้องหยุดใช้งานระบบ

```
เบราว์เซอร์ ──apiCall(action)──┬─ action อยู่ใน SQL_ACTIONS ─→ /api/schedule ─┐
                               └─ นอกนั้น ────────────────────→ Google Apps Script (ชีทเดิม)
                                                                              │
                    office-server :8787/schedule ←──────────────────────────┘
                    (เครื่องที่ออฟฟิศ) ──localhost:1433──→ SQL Server narai_hr
```

**ทำไมต้องอ้อมผ่าน office-server:** ไฟร์วอลล์ของออฟฟิศเปิดพอร์ต 1433 ให้เฉพาะ IP ในไทย
แต่ฟังก์ชันบน Vercel วิ่งมาจากต่างประเทศ จึงต่อฐานข้อมูลตรงไม่ได้ — กดบันทึกตารางแล้วขึ้น error มาตลอด
เครื่องที่ออฟฟิศต่อ SQL Server ผ่าน `localhost` ได้อยู่แล้ว (ไม่ผ่านไฟร์วอลล์) และ Vercel ก็เรียก
เครื่องนั้นที่พอร์ต 8787 ได้อยู่แล้ว (หน้ายอดขาย/สต๊อกใช้ทางนี้ทุกวัน) จึงต่อกันสองทอดแทน
เป็นแพตเทิร์นเดียวกับที่ใช้กับ ZKBio9 อยู่ก่อนแล้ว

## การล็อกอิน — ย้ายมาที่ตาราง `hr_user` แล้ว

เดิมหน้าล็อกอินอ่านชีท **User** ผ่าน Apps Script (คอลัมน์ A/B/C/D = username / password / สาขา / outlet id)
ตอนนี้ย้ายมาตรวจกับตาราง **`dbo.hr_user`** ใน `narai_hr` เหมือน action อื่นๆ

```
เบราว์เซอร์ ──loginUser()──→ /api/schedule ──→ office-server ──→ SELECT dbo.hr_user
                                                     │
                                                     └─ ไม่เจอชื่อนี้ / รหัสไม่ตรง
                                                        └──→ ถามชีท User (ทางถอย) แล้วคัดลอกเข้ามาให้
```

### รหัสผ่านไม่ใช่ข้อความล้วนอีกแล้ว

ชีทเดิมเก็บรหัสเป็นข้อความล้วน ใครเปิดชีทได้ก็อ่านรหัสของทุกสาขาได้ทันที
ตาราง `hr_user` เก็บเป็นค่าที่ย้อนกลับไม่ได้แทน (scrypt — ดู `office-server/hr-password.js`)
ข้อมูลในตารางหลุดออกไปก็เอาไปล็อกอินไม่ได้

### ไม่ต้องรันสคริปต์ย้ายข้อมูล — ย้ายเองตอนคนนั้นล็อกอิน

ครั้งแรกที่ใครล็อกอินแล้วยังไม่มีชื่อใน `hr_user` ระบบจะไปถามชีทให้ตามเดิม
ถ้าชีทบอกว่าผ่าน ก็คัดลอกผู้ใช้คนนั้นเข้าตารางพร้อมเข้ารหัสรหัสผ่านให้เลย
**ครั้งต่อไปคนนั้นจะเข้าทาง SQL ล้วนๆ ไม่แตะชีทอีก**

จึงไม่มีช่วงที่ใครล็อกอินไม่ได้ ไม่ต้องนัดเวลาปิดระบบ และไม่ต้องกรอกผู้ใช้ลงตารางเองทีละคน

> **ทำไมไม่เขียนสคริปต์ย้ายเหมือนพนักงาน/ตารางงาน:** สคริปต์พวกนั้นอ่านชีทผ่าน gviz
> ซึ่งต้องตั้งชีทเป็น "ผู้ที่มีลิงก์ • ผู้อ่าน" ก่อน — ชีท User มีรหัสผ่านของทุกสาขาอยู่
> การเปิดลิงก์สาธารณะแม้ชั่วคราวคือเอารหัสทั้งหมดไปวางไว้กลางแจ้ง จึงย้ายผ่านการล็อกอินจริงแทน

ชีทยังถูกถามอีกกรณีเดียว คือรหัสใน SQL ไม่ตรงกับที่กรอกมา (เช่น เพิ่งไปแก้รหัสในชีท)
ถ้าชีทผ่าน ระบบจะอัปเดตรหัสใหม่ลง `hr_user` ให้ — แก้รหัสที่ชีทเหมือนเดิมจึงยังใช้ได้ระหว่างช่วงเปลี่ยนผ่าน

**เมื่อทุกสาขาล็อกอินครบแล้ว** ตัดชีทออกจากเส้นทางล็อกอินถาวรได้ด้วยการตั้ง `SHEET_LOGIN_URL=off`
ใน `.env` ของ office-server แล้วรีสตาร์ทบริการ จากนั้นการเพิ่ม/แก้ผู้ใช้ต้องทำที่ตาราง (ดูหัวข้อถัดไป)

### เพิ่มผู้ใช้ / รีเซ็ตรหัสด้วยมือ

```powershell
cd <โฟลเดอร์ office-server>
node scripts/hash-password.mjs "รหัสที่ต้องการ"
```

สคริปต์จะพิมพ์คำสั่ง SQL ที่วางลง SSMS ได้เลย (แก้ชื่อผู้ใช้/สาขา/outlet id ให้ตรงก่อนรัน)

ถ้าจะพิมพ์รหัสเป็นข้อความล้วนลงคอลัมน์ `password_hash` ตรงๆ ก็ได้เหมือนกัน ระบบยอมรับ
แล้วจะเข้ารหัสทับให้เองตอนคนนั้นล็อกอินครั้งถัดไป — แต่ระหว่างนั้นรหัสจริงจะนอนอยู่ในตารางแบบอ่านได้
ใช้สคริปต์ข้างบนดีกว่า

ปิดบัญชีชั่วคราว: `UPDATE dbo.hr_user SET is_active = 0 WHERE username = N'...'`
(ปิดแล้วเข้าไม่ได้จริง ระบบจะไม่ไปถามชีทต่อให้)

### ทางถอยเมื่อ office-server ล่ม

`loginUser()` ใน `src/services/api.js` แยกสาเหตุที่ล้มออกจากกัน

| SQL ตอบว่าอะไร | หน้าเว็บทำต่อ |
|---|---|
| รหัสไม่ถูก / บัญชีถูกปิด | แสดง error จบ — ไม่ถามชีทซ้ำ (office-server ถามให้แล้ว) |
| ต่อไม่ได้ / ตอบ 5xx | ไปถามชีทเองโดยตรง แล้วเข้าระบบได้ตามปกติ |

เพราะ action อื่นถ้า office-server ล่มก็แค่หน้านั้นใช้ไม่ได้ แต่ถ้าล็อกอินล่มด้วยคือเข้าไม่ได้เลยสักหน้า
รวมถึงหน้าที่ยังวิ่งไปชีทและทำงานได้ปกติอยู่ (หน้ารายชื่อพนักงาน หน้ารับของ หน้าใบเบิก)

### user ที่ล็อกอินแล้ว ใช้ต่ออย่างไร

`AuthContext` เก็บ user ไว้ที่ `localStorage['hr_user']` แล้ว `apiCall()` แนบไปกับทุกคำสั่งที่วิ่งไป SQL
ให้เองในฟิลด์ `_user` **ฝั่ง SQL ไม่มีการล็อกอินซ้อนอีกชั้น** หน้าเว็บไม่ต้องส่งชื่อผู้ใช้/ชื่อผู้อนุมัติเองอีกต่อไป

| ใช้ทำอะไร | เดิม | ตอนนี้ |
|---|---|---|
| คนที่กดบันทึก (`updated_by`, `hr_timesheet_log.actor`) | ไม่ได้เก็บ | มาจาก user ที่ล็อกอินไว้ |
| ชื่อผู้อนุมัติ OT | หน้าเว็บส่ง `approverName` มาเอง | มาจาก user ที่ล็อกอินไว้ (ปลอมจากหน้าเว็บไม่ได้) |
| จำกัดสาขา | หน้าเว็บล็อกอย่างเดียว | เซิร์ฟเวอร์บังคับอีกชั้น — ไม่ใช่สิทธิ์ `all` เห็นได้แค่สาขาตัวเอง |

ถ้า `_user` หายไป (ล้าง localStorage หรือยังไม่ได้ล็อกอิน) endpoint ตอบ 401
พร้อมข้อความ "เซสชันหมดอายุ กรุณาเข้าสู่ระบบใหม่" — ยกเว้น action `login` เองที่เรียกได้โดยยังไม่มีเซสชัน

> **ข้อจำกัดที่ยังเหลืออยู่:** `_user` มาจาก localStorage ของเบราว์เซอร์ ซึ่งผู้ใช้แก้เองได้
> การจำกัดสาขาจึงกันการกดผิดสาขาโดยไม่ตั้งใจได้ แต่กันคนที่ตั้งใจปลอมไม่ได้
> การย้ายล็อกอินมา SQL ยังไม่ได้แก้ข้อนี้ — ถ้าต้องการกันจริง ต้องให้ `login` ออก token ที่เซ็นชื่อไว้
> แล้วตรวจ token ที่ `/api/schedule` แทนการเชื่อ `_user` ที่ส่งมา

## ขั้นตอนติดตั้ง

### 1. เปิดทางให้ต่อฐานข้อมูลได้

**ไม่ต้องเปิดพอร์ต 1433 ออกเน็ตแล้ว** เพราะ office-server ต่อฐานข้อมูลผ่าน `localhost`
สิ่งที่ต้องมีคือ

- เปิด **TCP/IP protocol** ใน SQL Server Configuration Manager (ปกติปิดมาจากโรงงาน)
- เปิด **SQL Server Authentication** (โหมดผสม) ไม่ใช่ Windows Authentication อย่างเดียว
- office-server (พอร์ต 8787) ต้องรันอยู่และ Vercel เรียกถึง — ซึ่งเป็นเงื่อนไขเดียวกับหน้ายอดขาย/สต๊อก
  ที่ใช้อยู่ทุกวันแล้ว ไม่มีอะไรต้องตั้งเพิ่ม

### 2. สร้างตาราง

```cmd
sqlcmd -S 203.154.185.48 -U sa -P "<รหัสผ่าน>" -i docs\schema-hr.sql
```

แล้วสร้าง login แยกสำหรับเว็บ (อย่าใช้ `sa`) ตามคำสั่งท้ายไฟล์ `schema-hr.sql`

### 3. ตั้งค่าการเชื่อมต่อ — ที่ `.env` ของ office-server ไม่ใช่ที่ Vercel

แก้ `<โฟลเดอร์ office-server>\.env` (ดูตัวอย่างครบใน `.env.example`)

| ตัวแปร | ค่า |
|---|---|
| `HR_DB_HOST` | `localhost` |
| `HR_DB_NAME` | `narai_hr` |
| `HR_DB_USER` | login ที่สร้างไว้ เช่น `narai_web` |
| `HR_DB_PASSWORD` | รหัสผ่านของ login นั้น |
| `HR_DB_INSTANCE` | ใส่เมื่อเป็น named instance เช่น `SQLEXPRESS` (ปกติเว้นว่าง) |
| `HR_DB_PORT` | ใส่เมื่อไม่ใช่ 1433 (ปกติเว้นว่าง) |
| `SHEET_LOGIN_URL` | ปกติเว้นว่าง (ใช้ URL ของ Apps Script เดิมเป็นทางถอยตอนล็อกอิน) ตั้งเป็น `off` เมื่อย้ายผู้ใช้ครบแล้ว |

แล้วรีสตาร์ทบริการ (PowerShell แบบ Run as Administrator)

```powershell
Restart-Service NaraiUsageAPI
```

ฝั่ง Vercel ใช้แค่ `USAGE_API_BASE` ที่ตั้งไว้อยู่แล้ว — **`HR_DB_*` บน Vercel ไม่ได้ใช้แล้ว ลบทิ้งได้**

ถ้ายังไม่ได้ตั้ง `HR_DB_USER`/`HR_DB_PASSWORD` endpoint จะตอบ 503
พร้อมข้อความบอกว่ายังไม่ได้ตั้งค่า แทนที่จะค้างรอจนหมดเวลา

### 3.1 ทดสอบว่าบันทึกลงฐานข้อมูลได้จริง

```powershell
cd <โฟลเดอร์ office-server>
node scripts/test-schedule.mjs
```

ยิงเข้า office-server เหมือนที่หน้าเว็บทำ (ping → บันทึก → อ่านกลับ) แล้วไปอ่านจากตารางใน
SQL Server ตรงๆ เพื่อยืนยันว่าแถวลงจริง ไม่ใช่แค่ API ตอบว่าสำเร็จ
ใช้ข้อมูลปลอม (สาขา `ZZTEST` วันที่ `2099-12-31`) แล้วลบทิ้งเมื่อจบ ใส่ `--keep` ถ้าอยากให้เหลือไว้ดูเอง

### 3.2 ทดสอบว่าล็อกอินตรวจกับตารางจริง

```powershell
cd <โฟลเดอร์ office-server>
node scripts/test-login.mjs
```

เช็คให้ครบทั้งรหัสถูก/รหัสผิด/ชื่อผู้ใช้ที่ไม่มีอยู่/บัญชีที่ถูกปิด แล้วไปอ่านตาราง `hr_user`
ตรงๆ เพื่อยืนยันสองข้อที่ API บอกเองไม่ได้ — ผู้ใช้ลงตารางจริง และรหัสในตารางไม่ใช่รหัสจริง
ใช้ผู้ใช้ปลอมชื่อ `zztest_login` ที่สคริปต์ใส่เอง แล้วลบทิ้งเมื่อจบ ไม่แตะผู้ใช้จริงและไม่แตะชีทเลย

### 4. ย้ายข้อมูลเก่า

ชีท 2 ไฟล์ต้องตั้งลิงก์เป็น **"ผู้ที่มีลิงก์ • ผู้อ่าน"** ก่อน
(สคริปต์อ่านผ่าน gviz แบบไม่ล็อกอิน ถ้าชีทปิดอยู่จะได้หน้า login กลับมาแทนข้อมูล)

| ชีท | ไอดี |
|---|---|
| พนักงาน | `1Abot2hKLUO6_z8NRW6c9A0m0ggra3ZE7Yq10kcUPr7Y` |
| ลงตารางงาน | `1bGSENQjSmmYv8V84aInyqk-K7r4niSXFlPqv0zEFQ1U` |

```bash
export HR_DB_USER=narai_web HR_DB_PASSWORD='...'

# ดูก่อนว่าจะย้ายกี่แถว และจับคอลัมน์ถูกไหม ยังไม่เขียนจริง
node scripts/migrate-schedule.mjs --months=6 --dry-run

# ย้ายจริง
node scripts/migrate-schedule.mjs --months=6
```

สคริปต์ย้าย 2 ชุด: พนักงาน (สร้างรายชื่อสาขาให้ด้วย) → ตารางงาน
รันซ้ำได้ (ใช้ MERGE ทับของเดิม ไม่เกิดแถวซ้ำ) เลือกเฉพาะบางชุดด้วย `--only=timesheet` ได้

**ชีทพนักงานจับคอลัมน์จากชื่อหัวตาราง ไม่ใช่ตำแหน่ง** เพราะไฟล์ถูกย้ายมาแล้วครั้งหนึ่ง
(ไม่ใช่ไฟล์เดียวกับที่ Apps Script เดิมชี้ไว้) ตำแหน่งคอลัมน์จึงเชื่อไม่ได้
`--dry-run` จะพิมพ์ออกมาว่าจับได้คอลัมน์ไหน — **ต้องตรวจให้ตรงทุกช่องก่อนย้ายจริงเสมอ**

```
  hrCode      <- C "รหัสพนักงาน"
  branch      <- E "สาขา"
  name        <- D "ชื่อ-สกุล"
  ...
```

ถ้าบรรทัดไหนขึ้นว่า `(ไม่พบหัวคอลัมน์ ใช้ตำแหน่งเดิม)` แปลว่าเดาไม่ออก
ต้องไปแก้ `EMP_COLUMNS` ในสคริปต์ให้ตรงกับหัวตารางจริงก่อน

### เป้าขาย / ค่าแรงสูงสุด / ยอดขายรายวัน

ชีท `Details` และ `ยอดขายสาขา` เลิกใช้แล้ว จึงไม่มีการย้ายเข้า SQL
ผลคือการ์ดบนหน้าลงตารางจะขึ้น 0 จนกว่าจะกรอกเป้าลงตาราง `hr_branch` เอง

```sql
UPDATE dbo.hr_branch SET daily_target = 40000, max_wage = 6000 WHERE branch = N'<รหัสสาขา>';
```

ส่วน "ยอดขายของวัน" ในหน้าประวัติจะเป็น 0 เสมอจนกว่าจะมีแหล่งข้อมูลใหม่
(ระบบมี `/api/dashboard` ที่ดึงยอดขายจริงจาก POS อยู่แล้ว ต่อเข้ามาแทนได้ถ้าต้องการ)

## สิ่งที่เปลี่ยนไปจากของเดิม

**ชีทเดิมเป็น log ต่อท้ายอย่างเดียว** — กดบันทึกวันเดิมซ้ำก็ได้แถวใหม่เรื่อยๆ
แล้วตอนอ่านค่อยหยิบแถวล่าสุดมาใช้ ชีทจึงบวมและอ่านช้าลงทุกสัปดาห์

ใน SQL เก็บ **หนึ่งแถวต่อพนักงานต่อวัน** (PK = `work_date` + `branch` + `hr_code`)

| การกระทำ | ชีทเดิม | SQL |
|---|---|---|
| บันทึกซ้ำวันเดิม | ต่อท้ายแถวใหม่ | `MERGE` ทับแถวเดิม |
| ล้างข้อมูลของวัน | ต่อท้ายแถวที่เขียนว่า `ล้างข้อมูล` | `DELETE` แถวนั้นจริง |
| ประวัติว่าใครแก้เมื่อไหร่ | ดูจากแถวเก่าที่ทับถมกัน | ตาราง `hr_timesheet_log` แยกต่างหาก (เก็บ actor + payload) |
| อนุมัติ OT | จับคู่ด้วย "ชื่อ" | จับคู่ด้วย `hr_code` (ชื่อซ้ำกันไม่โดนอนุมัติพร้อมกัน) |

เวลาเข้า/ออกเก็บเป็นข้อความ `HH:mm` ไม่ใช่ชนิด `TIME`
เพราะระบบเดิมใช้ค่า `24:00` ได้จริง (กะที่จบเที่ยงคืนพอดี) ซึ่ง `TIME` เก็บไม่ได้

## ข้อจำกัดของ Vercel ที่ต้องรู้

แผนที่ใช้อยู่จำกัด **12 Serverless Functions** และเต็มพอดีอยู่แล้ว
การเพิ่ม `api/schedule.js` จึงต้องยุบ `api/usagebytable.js` เข้าไปเป็นโหมดหนึ่ง
ของ `api/usagemenu.js` (`?bytable=1`) ก่อน — เหมือนที่ `api/dashboard.js`
รวมหลายโหมดไว้ในไฟล์เดียวอยู่แล้ว

**ถ้าจะย้าย action กลุ่มอื่นเพิ่ม ให้เพิ่มเป็น action ใน `api/schedule.js`
หรือไฟล์ที่มีอยู่แล้ว อย่าสร้างไฟล์ใหม่ใน `api/`** เพราะจะเกินลิมิตทันที

## รายชื่อพนักงาน — อ่านจาก SQL แต่แก้ไขที่ชีทเหมือนเดิม

`getScheduleEmployees` **ย้ายไป SQL แล้ว** (กลุ่มที่ 2 ใน `SQL_ACTIONS`) แต่ไม่ใช่การย้ายขาด
ยังผูกกับชีทอยู่สองทาง เพราะการเพิ่มคน/ให้ลาออก/แก้ค่าแรง ยังทำที่หน้ารายชื่อพนักงาน
ซึ่งเขียนลง Google Sheet เหมือนเดิมทุกอย่าง

**ห้ามเรียก `apiCall('getScheduleEmployees')` ตรงๆ** ให้ใช้ `fetchScheduleEmployees()` เสมอ
เพราะมันจัดการ fallback ตอน SQL ว่าง และการซิงก์กลับให้ครบ

ลำดับการทำงานของ `fetchScheduleEmployees()`:

1. อ่านจาก **SQL ก่อน** — เร็วกว่าชีทมาก (เหตุผลที่ย้าย: หน้าลงตารางรายสัปดาห์เคยโหลดช้า)
2. ถ้า SQL **ว่างหรือต่อไม่ได้** → ถอยไปอ่านจากชีท แล้วคืนค่านั้นแทน
   (กันเคสที่เคยพลาดมาแล้ว: เปิด action นี้ทั้งที่ `hr_employee` ยังว่าง ทำให้หน้านับสต๊อกดรอปดาวน์ว่างทั้งหน้า)
3. ถ้า SQL **มีข้อมูล** → คืนทันที แล้วอ่านชีทเงียบๆ ข้างหลัง ถ้ารายชื่อไม่ตรงกับใน SQL
   จะเรียก `onRefresh(fresh)` ให้หน้าอัปเดตตัวเอง — แก้ชีทแล้วเห็นผลในรอบถัดไปโดยไม่ต้องรอ
4. ผลที่ได้จากชีททุกครั้งจะถูกส่งไปเก็บใน `hr_employee` ด้วย (`syncEmployees` ยิงแบบไม่รอผล)

```
หน้ารายชื่อพนักงาน ──เพิ่ม/ลาออก/แก้ค่าแรง──→ Google Sheet   (ตัวหลักของการแก้ไข)
                                                    │
หน้าลงตาราง / หน้านับสต๊อก                          │
  └─ fetchScheduleEmployees()                       │
       ├─ 1. อ่าน hr_employee ใน SQL ──→ แสดงผลทันที │
       ├─ 2. SQL ว่าง/พัง ──────────────────────────┤ ใช้ชีทแทน
       └─ 3. เช็คชีทข้างหลัง ต่างเมื่อไหร่ ─────────┘ อัปเดตหน้าให้เอง
                                    │
                                    └──syncEmployees──→ hr_employee (คัดลอกตาม)
```

หน้ารายชื่อพนักงาน (`EmployeeList.jsx`) ใช้ action คนละตัวคือ `getEmployees`
ซึ่ง **ยังไม่ได้ย้าย** วิ่งไป Apps Script/ชีทอย่างเดียว

ฝั่ง SQL ปรับตามให้เอง: คนใหม่เพิ่มเข้ามา, คนที่หายไปจากรายชื่อตั้งเป็น `ลาออก`
(ไม่ลบแถว เพราะกะเก่ายังอ้างอิง `hr_code` อยู่)

**เหตุผลที่สำคัญกว่าความสะดวก:** วิธีนี้ทำให้ SQL ได้ "รหัสพนักงานชุดเดียวกับที่
หน้าเว็บใช้" เป๊ะ ไม่ต้องเดาว่ารหัสในชีท HR (`0808001`) กับในตารางงาน (`740808001`)
ตัวไหนถูก ซึ่งเป็นปัญหาที่ทำให้ตอนย้ายข้อมูลครั้งแรกกะ 72% หาเจ้าของไม่เจอ

**กันพลาดไว้แล้ว:** ถ้ารายชื่อที่ส่งมาน้อยกว่าครึ่งของจำนวนคนที่ยังทำงานอยู่ใน SQL
จะไม่ตั้งใครเป็นลาออกเลย เพราะกรณีนั้นน่าจะเป็นชีทตอบมาไม่ครบ ไม่ใช่คนลาออกยกสาขา

## ที่ยังไม่ได้ย้าย

`getBranches` ยังวิ่งไปชีทอยู่ ทั้งที่ `/api/schedule` รองรับแล้ว
เพราะมีอีก 7 หน้าที่ไม่เกี่ยวกับตารางงานใช้ action นี้ (บางหน้าอ่าน `outletId` ด้วย)
จะย้ายพร้อมกลุ่มของหน้าเหล่านั้นทีเดียว จะได้ทดสอบพร้อมกัน —
เมื่อพร้อมแล้วแค่เพิ่มชื่อ action ลงใน `SQL_ACTIONS`

action ที่เหลือของระบบ (ของเสีย, รับของ, ค่าใช้จ่าย, ปิดรอบสิ้นเดือน, พนักงาน)
ยังอยู่บน Apps Script ทั้งหมด — ดูหัวข้อถัดไป

`login` ย้ายมา SQL แล้ว (ตาราง `hr_user`) แต่ยังเรียกชีทเป็นทางถอยอยู่จนกว่าทุกสาขาจะล็อกอินครบ
แล้วตั้ง `SHEET_LOGIN_URL=off` — ดูหัวข้อ "การล็อกอิน" ด้านบน

ส่วน **หน้านับสต๊อก** เริ่มย้ายแล้ว (ตาราง + สคริปต์ย้ายข้อมูล + ฝั่งอ่าน)
รายละเอียดและลำดับที่เหลืออยู่ใน [stock-sql-migration.md](stock-sql-migration.md)

## ย้ายส่วนที่เหลือต่อ

ต้องรู้ก่อนว่าแต่ละส่วนอ่าน-เขียนชีทไหน คอลัมน์ไหน และมีกติกาการคำนวณอะไรซ่อนอยู่
ซอร์ส Apps Script ของทั้งระบบอยู่ในรีโปแล้วที่ `apps-script.js` (ตอนย้ายส่วนตารางงาน
ยังมีแค่ `indexลงตารางงาน.txt` จึงย้ายได้เฉพาะส่วนนั้นก่อน) — ไฟล์นั้นมี handler
ของทุก action ครบ ดูได้ว่าแต่ละตัวเปิดสเปรดชีตไหนและอ่านคอลัมน์ที่เท่าไหร่

ลำดับที่แนะนำ

1. **พนักงาน** (`getEmployees`, `addEmployee`, `resignEmployee`, `getNextHrCode`,
   `updateEmployeeLoga`, `uploadEmployeePhoto`) — ตาราง `hr_employee` มีอยู่แล้ว
   เหลือแค่ทำ action เพิ่ม รูปพนักงานต้องตัดสินใจว่าจะเก็บที่ไหน (ตอนนี้อยู่บน Drive)
2. **สาขา** (`getBranches`) — ย้ายพร้อมข้อ 1 แล้วทดสอบทั้ง 7 หน้าที่ใช้
3. **สต๊อก** — เริ่มไปแล้ว ดู [stock-sql-migration.md](stock-sql-migration.md)
4. **ของเสีย / รับของ / ค่าใช้จ่าย / ปิดรอบสิ้นเดือน** — แต่ละอันมีชีทของตัวเอง แยกทำทีละอันได้

**login ย้ายแล้ว** — อยู่ที่ตาราง `hr_user` พร้อมเข้ารหัสรหัสผ่านเรียบร้อย
(ดูหัวข้อ "การล็อกอิน" ด้านบน) ที่ยังเหลือคือการออก token ที่เซ็นชื่อไว้ตอนล็อกอิน
เพื่อเลิกเชื่อ `_user` ที่ฝั่งเบราว์เซอร์ส่งมา — ทำแยกทีหลังได้ ไม่ผูกกับการย้ายชีท
