# แก้ปัญหา "ติดต่อเซิร์ฟเวอร์ไม่ได้"

## ระบบนี้พึ่งเซิร์ฟเวอร์ 3 ที่ ไม่ใช่ที่เดียว

| ชั้น | ใช้ทำอะไร | ขึ้นที่หน้าไหน | จุดที่พังบ่อย |
|---|---|---|---|
| **Google Apps Script** (`src/services/api.js`) | ล็อกอิน, รายการสินค้า, นับสต๊อก, ตารางงาน, WASTE, ปิดยอด | เกือบทุกหน้า | โดนลิมิต execution พร้อมกัน / เปิดสเปรดชีตใหญ่ช้า |
| **office-server** ที่ออฟฟิศ (`office-server/`) ผ่าน `storenarai.dyndns.tv:8787` | แดชบอร์ด, ยอดขาย, ยอดใช้ตามเมนู (BOM), บิล | แดชบอร์ด, ค้นหารายการขาย, ยอดใช้ในหน้านับสต๊อก | เครื่อง IT-Narai ปิด / เน็ตออฟฟิศหลุด / IP dyndns เปลี่ยน / พอร์ต 8787 ไม่เปิด |
| **MySQL** ที่ `inventory.dyndns.tv` (`api/orderd.js`, `withdrawals.js`, `pending_orders.js`, `insert_order.js`) | ใบรับ, ใบเบิก, ใบเบิกค้าง, ส่งใบสั่งของ | หน้านับสต๊อก (ยอดรับเข้า/ใบเบิก/สั่งของ) | เครื่องปลายทางปิด / connection ค้างตายหลัง Vercel แช่แข็งฟังก์ชัน |

**"เชื่อมต่อเซิร์ฟเวอร์ไม่สำเร็จ" ที่เห็นเป็นข้อความรวมของทั้ง 3 ชั้น** ตอนนี้ข้อความ error บอกสาเหตุจริงแล้ว
(เช่น "เครื่อง IT-Narai อาจปิดอยู่", "dyndns อาจยังไม่อัปเดต IP ใหม่") ให้อ่านข้อความนั้นก่อนเสมอ

## ระบบกันพลาดที่ใส่ไว้แล้ว

- **ลองใหม่อัตโนมัติ** เมื่อพลาดแบบชั่วคราว (เน็ตกระตุก, เซิร์ฟเวอร์ตอบ 5xx, GAS ตอบหน้า HTML แทน JSON)
  - **เฉพาะคำสั่งอ่าน** เท่านั้น — คำสั่งบันทึก/ส่งใบเบิกจะไม่ลองใหม่ เพื่อกันข้อมูลซ้ำ
- **timeout** ทุกจุด (ไม่ปล่อยให้ค้างรอตลอดไป) พร้อมเวลารวมสูงสุดต่อคำขอ
- **จำกัดการยิงพร้อมกันไปที่ GAS ไว้ที่ 3** เพราะเกินนั้น Google จะเริ่มปฏิเสธ
- **หนึ่ง endpoint พลาด ไม่ทำให้ทั้งหน้าพัง** — หน้านับสต๊อกยังเปิดทำงานได้แม้ยอดรับเข้า/ใบเบิกค้างโหลดไม่ได้

## ขึ้น "เครื่อง IT-Narai อาจปิดอยู่" — ใช้สคริปกู้

**1) เปิดเครื่อง IT-Narai ก่อน** (ถ้าเครื่องดับอยู่ ไม่มีอะไรสั่งจากระยะไกลได้)
service ตั้งให้สตาร์ทเองตอนเปิดเครื่องอยู่แล้ว รอ 3-4 นาที (ระบบอุ่นข้อมูลย้อนหลัง) แล้วลองหน้าเว็บดูก่อน

**2) ถ้าเปิดเครื่องแล้วหน้าเว็บยังไม่ขึ้น** ให้รันสคริปตรวจ+ซ่อมบนเครื่องนั้น
(คลิกขวาที่ PowerShell → **Run as administrator**):

```powershell
cd <โฟลเดอร์โค้ด>\office-server\scripts
powershell -ExecutionPolicy Bypass -File .\fix-narai-api.ps1
```

สคริปจะไล่ตรวจให้ทีละชั้นแล้วซ่อมเท่าที่ซ่อมได้: Node.js → service (สตาร์ท/ตั้งให้ขึ้นเองตอนเปิดเครื่อง)
→ `/health` (รีสตาร์ทให้ถ้าค้าง) → firewall (เปิดพอร์ตให้) → **dyndns ชี้ IP ถูกตัวหรือเปล่า**
ชั้นไหนซ่อมเองไม่ได้จะบอกว่าต้องทำอะไรต่อ

**3) กันไม่ให้ดับซ้ำ** — รันซ้ำอีกรอบด้วย `-Harden`

```powershell
powershell -ExecutionPolicy Bypass -File .\fix-narai-api.ps1 -Harden
```

เพิ่มให้อีก 3 อย่าง: ตั้งไม่ให้เครื่องหลับ/จำศีล, ให้ Windows รีสตาร์ท service เองเมื่อโปรเซสตาย,
และติดตั้ง **ตัวเฝ้าระวังทุก 5 นาที** (`narai-watchdog.ps1`) ที่จะรีสตาร์ทให้เองเมื่อ `/health` ไม่ตอบ
— ครอบคลุมอาการที่โปรเซสยังอยู่แต่ค้างไม่รับ request ซึ่ง Windows ไม่ถือว่าแครชจึงไม่รีสตาร์ทให้
(log อยู่ที่ `office-server\logs\watchdog.log`)

> ทำครั้งเดียวพอ ไม่ต้องรันซ้ำทุกครั้ง

**ถ้าเครื่องนั้นใช้ PowerShell ไม่ได้** (ถูกปิดใช้งาน / ติด policy) มีเวอร์ชัน `.cmd` ที่ทำงานเหมือนกัน
ใช้แค่คำสั่งพื้นฐานของ Windows (`sc`, `netsh`, `schtasks`, `curl`) — คลิกขวาที่ไฟล์ → **Run as administrator**

```cmd
cd /d <โฟลเดอร์โค้ด>\office-server\scripts
fix-narai-api.cmd
fix-narai-api.cmd harden     :: + กันดับซ้ำ (ทำครั้งเดียวพอ)
```

ต่างจากเวอร์ชัน PowerShell เล็กน้อย: ตรงขั้นเทียบ IP จะพิมพ์ค่าทั้งสองออกมาให้เทียบเอง
และต้องมี `curl` (มากับ Windows 10 build 1803 ขึ้นไป)

## เช็คทีละชั้นด้วยมือ (ถ้าไม่ใช้สคริป)

```powershell
# 1) office-server ยังทำงานอยู่ไหม (รันบนเครื่อง IT-Narai)
Get-Service NaraiUsageAPI
Start-Process http://localhost:8787/health
Restart-Service NaraiUsageAPI     # ถ้าค้าง

# 2) เข้าจากข้างนอกได้ไหม (รันจากที่ไหนก็ได้)
curl http://storenarai.dyndns.tv:8787/health
#    ตอบไม่ได้ = เครื่องปิด / dyndns ชี้ IP เก่า / router ไม่ได้ forward พอร์ต 8787
```

- **Google Apps Script**: เปิด [script.google.com](https://script.google.com) → โปรเจกต์ → **Executions** ดูว่ามี error หรือชนลิมิตไหม
- **ถ้า dyndns เปลี่ยน IP หรือย้ายพอร์ต**: ตั้ง env `USAGE_API_BASE` บน Vercel ทับได้เลย ไม่ต้องแก้โค้ด
  (ค่าเริ่มต้นอยู่ที่ `lib/upstream.js`)
- **MySQL**: ตั้ง env `MYSQL_HOST` / `MYSQL_PORT` / `MYSQL_USER` / `MYSQL_PASSWORD` บน Vercel (ค่าเริ่มต้นอยู่ที่ `lib/mysql.js`)

## ตารางงาน/นับสต๊อกขึ้น "ชื่อผู้ใช้/รหัสผ่านไม่ถูกต้อง" ทั้งที่รหัสถูก

อาการหลอกที่สุดที่เคยเจอ — **รหัสผ่านถูกต้อง แต่ login ถูกล็อก**

`narai_web` เป็น SQL login ที่ office-server ใช้ต่อทั้ง `narai_hr` (ตารางงาน)
และ `InventoryNarai` (นับสต๊อก) ถ้ามันล็อก **สองหน้านั้นล่มพร้อมกัน**

เกิดจาก: เปลี่ยนรหัสใน SQL Server แต่ยังไม่ได้แก้ `.env` (หรือแก้แล้วยังไม่รีสตาร์ต)
office-server จะยิงล็อกอินด้วยรหัสเก่าซ้ำๆ ทุกครั้งที่มีคนเปิดหน้าเว็บ
ผิดครบตามนโยบาย Windows ภายในไม่กี่วินาที → บัญชีล็อกตัวเอง → ทุกทางเข้าไม่ได้หมด
รวมถึง `sqlcmd` ด้วย

### เช็คว่าใช่ไหม (รันบนเครื่องที่ออฟฟิศ)

```powershell
sqlcmd -S localhost -E -W -s"|" -Q "SELECT name, is_disabled, LOGINPROPERTY(name,'IsLocked') AS locked, LOGINPROPERTY(name,'IsMustChange') AS must_change, PWDCOMPARE('<รหัสที่คิดว่าถูก>', password_hash) AS pw_ok FROM sys.sql_logins WHERE name='narai_web'"
```

`locked = 1` พร้อม `pw_ok = 1` = **ถูกล็อก ไม่ใช่รหัสผิด**

### แก้

```powershell
sqlcmd -S localhost -E -d master -Q "ALTER LOGIN narai_web WITH CHECK_POLICY = OFF; ALTER LOGIN narai_web WITH PASSWORD = N'<รหัส>'; ALTER LOGIN narai_web ENABLE;"
Restart-Service NaraiUsageAPI
```

`CHECK_POLICY = OFF` ล้างสถานะล็อกและปิดการล็อกบัญชีของ login ตัวนี้ถาวร
**ตั้งใจให้เป็นแบบนั้น** เพราะเป็น login ของโปรแกรมไม่ใช่ของคน โปรแกรมยิงซ้ำอัตโนมัติเสมอ
ถ้ารหัสไม่ตรงชั่วคราวมันจะล็อกตัวเองแล้วทำให้ระบบล่มทั้งระบบ ซึ่งแย่กว่าความเสี่ยงที่กันได้

### เวลาจะเปลี่ยนรหัส `narai_web` ให้ทำตามลำดับนี้เสมอ

1. `Stop-Service NaraiUsageAPI` — หยุดก่อน อย่าให้มันยิงด้วยรหัสเก่า
2. เปลี่ยนรหัสใน SQL Server
3. แก้ `HR_DB_PASSWORD` ใน `office-server/.env`
4. `Start-Service NaraiUsageAPI`

สลับลำดับเมื่อไหร่ บัญชีจะล็อกตัวเองระหว่างทาง

### ยืนยันว่ากลับมาใช้ได้จริง

```powershell
cd D:\Narai-branch-main\office-server
node scripts/test-schedule.mjs
```

ทดสอบครบวงจรตั้งแต่ยิง API จนไปอ่านแถวจริงในตาราง SQL แล้วลบข้อมูลทดสอบทิ้งให้เอง

### เกร็ดตอนไล่หาสาเหตุ

- `sqlcmd -S localhost` กับ `sqlcmd -S tcp:localhost,1433` อาจให้ผลต่างกัน (คนละโปรโตคอล)
  ถ้าจะเทียบกับที่ Node เห็น ให้ใช้แบบ `tcp:` เสมอ
- สาเหตุจริงของ "Login failed" อยู่ในเลข State ของ error log ฝั่งเซิร์ฟเวอร์
  (ไดรเวอร์จะเห็นแค่ข้อความกลางๆ เพื่อความปลอดภัย):
  ```powershell
  sqlcmd -S localhost -E -Q "EXEC xp_readerrorlog 0, 1, N'Login failed', N'narai_web'" -W -s"|"
  ```
  State 8 = รหัสผิดจริง, 5 = ไม่มี login นี้, 7 = ถูก disable, 38/40 = เข้าฐานข้อมูลไม่ได้

## หน้า "ปิดยอดสิ้นเดือน" ขึ้น "เซิร์ฟเวอร์ตอบกลับช้าเกินไป (หมดเวลารอ)"

ข้อความนี้คือ fetch ถูกตัดตอนครบ timeout (`src/services/api.js`) ไม่ใช่เน็ตขาด สาเหตุที่เจอและแก้ไปแล้ว:

- หน้านี้เคยเรียก `getStockItems` ซึ่งอ่านชีท `ข้อมูลนับสตอค` 25,000+ แถว (~20 วิ) ทั้งที่ใช้แค่ รหัส/ชื่อ/หน่วย/ราคา
  → เปลี่ยนไปใช้ `getClosingItems` ที่อ่านเฉพาะชีท `item` ไฟล์เดียว พร้อมแคช 5 นาที
- `getMonthEndClosing` ไม่มีแคชและอ่านทั้งชีท `ปิดรอบสิ้นเดือน` ที่แถวสะสมขึ้นทุกเดือน
  → ใส่แคชต่อสาขา 2 นาที และล้างแคชอัตโนมัติทุกครั้งที่มีการบันทึกใหม่ของสาขานั้น
- เปิดหน้าเดียวยิง 2 คำสั่งพร้อมกัน ทำให้ไปเบียดโควตา execution ของ GAS เอง → เปลี่ยนเป็นโหลดทีละคำสั่ง
- `saveMonthEndClosing` เคยใช้ `appendRow` ทีละรายการ (200+ ครั้งต่อการกดบันทึก) → รวมเป็น `setValues` ครั้งเดียว

**ถ้ายังเจออาการนี้อีก** ให้ดู Executions ใน script.google.com ว่าคำสั่งไหนกินเวลานานสุด
และจำไว้ว่า **การ abort ฝั่งเบราว์เซอร์ไม่ได้หยุด GAS ที่กำลังรัน** — กดรีเฟรชรัวๆ จะยิ่งทำให้งานค้างซ้อนกัน

## หน้า "นับสต๊อกและขอเบิก" กดบันทึกแล้วขึ้น "เซิร์ฟเวอร์ตอบกลับช้าเกินไป (หมดเวลารอ)"

ข้อความเดียวกับหัวข้อบน คือ fetch โดนตัดตอนครบ timeout ระหว่างรอ `saveStock` ไม่ใช่เน็ตขาด สาเหตุและสิ่งที่แก้ไปแล้ว:

- `saveStock` เคยเขียนชีทในลูป **ทีละรายการ**: `ข้อมูลนับสตอค` appendRow 1 ครั้ง + `ยอดยกมา` setValue 2 ครั้ง
  (หรือ appendRow ถ้าเป็นสินค้าใหม่) + `ข้อมูลเบิก` appendRow 1 ครั้ง = คุยกับ Google Sheets **ได้ถึง 4 รอบต่อสินค้า 1 ตัว**
  สาขาหนึ่งกดบันทึกทีละ 200-300 รายการ = เขียนชีทเกือบพันครั้งต่อการกดหนึ่งครั้ง เกิน 30 วิ (timeout เดิม) แน่นอน
  → รวบเป็น `setValues` ก้อนเดียวต่อชีท (แบบเดียวกับ `saveMonthEndClosing`)
- ตอนหาเลขที่ใบเบิกถัดไป เคยอ่านชีท `ข้อมูลเบิก` **ทั้ง 9 คอลัมน์** ทั้งที่ใช้แค่คอลัมน์ A และชีทนี้แถวสะสมขึ้นทุกวัน
  → อ่านเฉพาะคอลัมน์ A
- `setValues` ไม่ต่อท้ายให้อัตโนมัติเหมือน `appendRow` — สองสาขากดบันทึกพร้อมกันจะคำนวณแถวสุดท้ายได้เลขเดียวกันแล้วเขียนทับกันเงียบๆ
  → ใส่ `LockService` คร่อมช่วง "จองเลขที่ใบเบิก + เขียนต่อท้าย" (รอคิวได้ 30 วิ เกินนั้นตอบให้กดใหม่ ข้อมูลที่กรอกยังอยู่ครบ)
- หลังบันทึกเสร็จ ล้างแคช `stockItems_<สาขา>` ให้ด้วย ไม่งั้นหน้าจอโหลดซ้ำแล้วยังเห็นยอดเก่าค้างได้ถึง 90 วิ

ฝั่งเว็บ (`src/pages/StockList.jsx`):

- ให้เวลา `saveStock` 90 วิ (มากกว่าค่ามาตรฐาน 30 วิ) เพราะบันทึกทีเดียวหลายร้อยรายการ และอาจต้องรอคิวสาขาอื่น
- **ถ้าหมดเวลารอ ไม่ได้แปลว่าไม่ได้บันทึก** — การตัดฝั่งเบราว์เซอร์ไม่ได้หยุด Google Apps Script ที่กำลังเขียนอยู่
  ตอนนี้ข้อความเตือนจะบอกให้ไปเช็ค "ใบเบิกค้าง" หรือรีเฟรชก่อนกดบันทึกซ้ำ **ห้ามกดบันทึกซ้ำทันที** เพราะจะได้ยอดนับซ้ำและใบเบิกซ้อนอีกใบ

> แก้ที่ `apps-script.js` = ต้อง **Deploy ใหม่บน script.google.com** ถึงจะมีผล (ไฟล์ในรีโปเป็นสำเนาไว้ดู/แก้)
> เลือก Deploy → Manage deployments → แก้ deployment เดิม → New version เพื่อให้ URL เดิมใช้ได้ต่อ

## หน้า "ค้นหารายการขาย" / แดชบอร์ด / ตารางรายการขาย — รายการไม่ขึ้น

endpoint กลุ่มนี้ (`/api/dashboard`, `/api/dashboard?itemsales=1`, `/api/bills`) ให้ office-server
คำนวณข้ามทุกวันในช่วงที่เลือก — วันไหนยังไม่อยู่ในแคชรายวันต้องดึงจาก POS สด ใช้เวลาได้หลายสิบวินาที
(ตอน office-server เพิ่งรีสตาร์ทจะอุ่นแคชย้อนหลัง ~70 วันอยู่ ~3-4 นาที ช่วงนั้นจะช้าเป็นพิเศษ)

- เดิม timeout ฝั่ง Vercel ตัดที่ 20 วิ ทั้งที่ฟังก์ชันรอได้ถึง 60 วิ → คำนวณใกล้เสร็จก็โดนตัดทิ้ง รายการเลยไม่ขึ้น
  ตอนนี้ endpoint หนักพวกนี้รอ ~55 วิ (`HEAVY_UPSTREAM_OPTS` ใน `lib/upstream.js`)
  และฝั่งเบราว์เซอร์รอต่อรอบ 65 วิ รวมไม่เกิน ~2 นาที (`HEAVY_OPTS` ใน `src/services/dashboardApi.js`)
- การกดดึงซ้ำไม่เริ่มจากศูนย์ — office-server แคชวันที่คำนวณเสร็จแล้วไว้ รอบถัดไปเร็วขึ้นเรื่อยๆ
- ถ้ารอครบแล้วยังไม่ขึ้น ให้เช็คว่า office-server ยังทำงานอยู่ไหมตามหัวข้อ "เช็คทีละชั้น" ด้านบน
  (ขึ้นข้อความ "เครื่อง IT-Narai อาจปิดอยู่" = ต่อไม่ได้ตั้งแต่ต้น ไม่ใช่เรื่อง timeout)

## ที่ยังต้องแก้ที่ต้นเหตุ (โค้ดช่วยไม่ได้)

1. **เครื่องที่ออฟฟิศต้องเปิดตลอดเวลา** — ทั้ง office-server และ MySQL อยู่บนเน็ตออฟฟิศ
   เน็ตหลุด/ไฟดับ/เครื่องหลับ = ทุกสาขาใช้หน้าที่พึ่งข้อมูลพวกนี้ไม่ได้ทันที
2. **dyndns + UPnP ไม่ได้การันตี** — ถ้า router รีเซ็ต mapping หรือ IP เปลี่ยนเร็วกว่าที่ dyndns อัปเดต จะเข้าไม่ได้ช่วงหนึ่ง
   ทางแก้ระยะยาวคือขอ IP นิ่ง (fixed IP) หรือทำ tunnel ที่ไม่ต้องเปิดพอร์ต
3. **Google Apps Script มีเพดานการใช้งานต่อบัญชี** — ถ้าจำนวนสาขา/ผู้ใช้เพิ่มขึ้นอีก
   ทางแก้คือย้ายงานที่เรียกถี่ที่สุด (เช่น `getStockItems`) ออกจาก GAS ไปที่ office-server หรือฐานข้อมูลจริง
