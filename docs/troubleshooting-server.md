# แก้ปัญหา "ติดต่อเซิร์ฟเวอร์ไม่ได้"

## ระบบนี้พึ่งเซิร์ฟเวอร์ 3 ที่ ไม่ใช่ที่เดียว

| ชั้น | ใช้ทำอะไร | ขึ้นที่หน้าไหน | จุดที่พังบ่อย |
|---|---|---|---|
| **Google Apps Script** (`src/services/api.js`) | ล็อกอิน, รายการสินค้า, นับสต๊อก, ตารางงาน, WASTE, ปิดยอด | เกือบทุกหน้า | โดนลิมิต execution พร้อมกัน / เปิดสเปรดชีตใหญ่ช้า |
| **office-server** ที่ออฟฟิศ (`office-server/`) ผ่าน `storenarai.dyndns.tv:8787` | แดชบอร์ด, ยอดขาย, ยอดใช้ตามเมนู (BOM), บิล | แดชบอร์ด, ค้นหารายการขาย, ยอดใช้ในหน้านับสต๊อก | เครื่อง IT-Narai ปิด / เน็ตออฟฟิศหลุด / IP dyndns เปลี่ยน / พอร์ต 8787 ไม่เปิด |
| **MySQL** ที่ `inventory.dyndns.tv` (`api/orderd.js`, `withdrawals.js`, `pending_orders.js`, `insert_order.js`) | ใบรับ, ใบเบิก, ใบเบิกค้าง, ส่งใบสั่งของ | หน้านับสต๊อก (ยอดรับเข้า/ใบเบิก/สั่งของ) | เครื่องปลายทางปิด / connection ค้างตายหลัง Vercel แช่แข็งฟังก์ชัน |

**"เชื่อมต่อเซิร์ฟเวอร์ไม่สำเร็จ" ที่เห็นเป็นข้อความรวมของทั้ง 3 ชั้น** ตอนนี้ข้อความ error บอกสาเหตุจริงแล้ว
(เช่น "เครื่อง IT-Narai อาจปิดอยู่", "dyndns อาจยังไม่อัปเดต IP ใหม่") ให้อ่านข้อความนั้นก่อนเสมอ

## ระบบกันพลาดที่ใส่ไว้แล้ว

- **ลองใหม่อัตโนมัติ** เมื่อพลาดแบบชั่วคราว (เน็ตกระตุก, เซิร์ฟเวอร์ตอบ 5xx, GAS ตอบหน้า HTML แทน JSON)
  - **เฉพาะคำสั่งอ่าน** เท่านั้น — คำสั่งบันทึก/ส่งใบเบิกจะไม่ลองใหม่ เพื่อกันข้อมูลซ้ำ
- **timeout** ทุกจุด (ไม่ปล่อยให้ค้างรอตลอดไป) พร้อมเวลารวมสูงสุดต่อคำขอ
- **จำกัดการยิงพร้อมกันไปที่ GAS ไว้ที่ 3** เพราะเกินนั้น Google จะเริ่มปฏิเสธ
- **หนึ่ง endpoint พลาด ไม่ทำให้ทั้งหน้าพัง** — หน้านับสต๊อกยังเปิดทำงานได้แม้ยอดรับเข้า/ใบเบิกค้างโหลดไม่ได้

## เช็คทีละชั้นเวลามีปัญหา

```powershell
# 1) office-server ยังทำงานอยู่ไหม (รันบนเครื่อง IT-Narai)
Get-Service NaraiUsageAPI
Start-Process http://localhost:8787/health
Restart-Service NaraiUsageAPI     # ถ้าค้าง

# 2) เข้าจากข้างนอกได้ไหม (รันจากที่ไหนก็ได้)
curl http://storenarai.dyndns.tv:8787/health
#    ตอบไม่ได้ = เครื่องปิด / dyndns ชี้ IP เก่า / router ไม่ได้ forward พอร์ต 8787
```

- **Google Apps Script**: เปิด [script.google.com](https://script.google.com) → โปรเจกต์ → **Executions** ดูว่ามี error หรือชนลิมิตไหม
- **ถ้า dyndns เปลี่ยน IP หรือย้ายพอร์ต**: ตั้ง env `USAGE_API_BASE` บน Vercel ทับได้เลย ไม่ต้องแก้โค้ด
  (ค่าเริ่มต้นอยู่ที่ `lib/upstream.js`)
- **MySQL**: ตั้ง env `MYSQL_HOST` / `MYSQL_PORT` / `MYSQL_USER` / `MYSQL_PASSWORD` บน Vercel (ค่าเริ่มต้นอยู่ที่ `lib/mysql.js`)

## หน้า "ปิดยอดสิ้นเดือน" ขึ้น "เซิร์ฟเวอร์ตอบกลับช้าเกินไป (หมดเวลารอ)"

ข้อความนี้คือ fetch ถูกตัดตอนครบ timeout (`src/services/api.js`) ไม่ใช่เน็ตขาด สาเหตุที่เจอและแก้ไปแล้ว:

- หน้านี้เคยเรียก `getStockItems` ซึ่งอ่านชีท `ข้อมูลนับสตอค` 25,000+ แถว (~20 วิ) ทั้งที่ใช้แค่ รหัส/ชื่อ/หน่วย/ราคา
  → เปลี่ยนไปใช้ `getClosingItems` ที่อ่านเฉพาะชีท `item` ไฟล์เดียว พร้อมแคช 5 นาที
- `getMonthEndClosing` ไม่มีแคชและอ่านทั้งชีท `ปิดรอบสิ้นเดือน` ที่แถวสะสมขึ้นทุกเดือน
  → ใส่แคชต่อสาขา 2 นาที และล้างแคชอัตโนมัติทุกครั้งที่มีการบันทึกใหม่ของสาขานั้น
- เปิดหน้าเดียวยิง 2 คำสั่งพร้อมกัน ทำให้ไปเบียดโควตา execution ของ GAS เอง → เปลี่ยนเป็นโหลดทีละคำสั่ง
- `saveMonthEndClosing` เคยใช้ `appendRow` ทีละรายการ (200+ ครั้งต่อการกดบันทึก) → รวมเป็น `setValues` ครั้งเดียว

**ถ้ายังเจออาการนี้อีก** ให้ดู Executions ใน script.google.com ว่าคำสั่งไหนกินเวลานานสุด
และจำไว้ว่า **การ abort ฝั่งเบราว์เซอร์ไม่ได้หยุด GAS ที่กำลังรัน** — กดรีเฟรชรัวๆ จะยิ่งทำให้งานค้างซ้อนกัน

## หน้า "ค้นหารายการขาย" / แดชบอร์ด / ตารางรายการขาย — รายการไม่ขึ้น

endpoint กลุ่มนี้ (`/api/dashboard`, `/api/dashboard?itemsales=1`, `/api/bills`) ให้ office-server
คำนวณข้ามทุกวันในช่วงที่เลือก — วันไหนยังไม่อยู่ในแคชรายวันต้องดึงจาก POS สด ใช้เวลาได้หลายสิบวินาที
(ตอน office-server เพิ่งรีสตาร์ทจะอุ่นแคชย้อนหลัง ~70 วันอยู่ ~3-4 นาที ช่วงนั้นจะช้าเป็นพิเศษ)

- เดิม timeout ฝั่ง Vercel ตัดที่ 20 วิ ทั้งที่ฟังก์ชันรอได้ถึง 60 วิ → คำนวณใกล้เสร็จก็โดนตัดทิ้ง รายการเลยไม่ขึ้น
  ตอนนี้ endpoint หนักพวกนี้รอ ~55 วิ (`HEAVY_UPSTREAM_OPTS` ใน `lib/upstream.js`)
  และฝั่งเบราว์เซอร์รอต่อรอบ 65 วิ รวมไม่เกิน ~2 นาที (`HEAVY_OPTS` ใน `src/services/dashboardApi.js`)
- การกดดึงซ้ำไม่เริ่มจากศูนย์ — office-server แคชวันที่คำนวณเสร็จแล้วไว้ รอบถัดไปเร็วขึ้นเรื่อยๆ
- ถ้ารอครบแล้วยังไม่ขึ้น ให้เช็คว่า office-server ยังทำงานอยู่ไหมตามหัวข้อ "เช็คทีละชั้น" ด้านบน
  (ขึ้นข้อความ "เครื่อง IT-Narai อาจปิดอยู่" = ต่อไม่ได้ตั้งแต่ต้น ไม่ใช่เรื่อง timeout)

## ที่ยังต้องแก้ที่ต้นเหตุ (โค้ดช่วยไม่ได้)

1. **เครื่องที่ออฟฟิศต้องเปิดตลอดเวลา** — ทั้ง office-server และ MySQL อยู่บนเน็ตออฟฟิศ
   เน็ตหลุด/ไฟดับ/เครื่องหลับ = ทุกสาขาใช้หน้าที่พึ่งข้อมูลพวกนี้ไม่ได้ทันที
2. **dyndns + UPnP ไม่ได้การันตี** — ถ้า router รีเซ็ต mapping หรือ IP เปลี่ยนเร็วกว่าที่ dyndns อัปเดต จะเข้าไม่ได้ช่วงหนึ่ง
   ทางแก้ระยะยาวคือขอ IP นิ่ง (fixed IP) หรือทำ tunnel ที่ไม่ต้องเปิดพอร์ต
3. **Google Apps Script มีเพดานการใช้งานต่อบัญชี** — ถ้าจำนวนสาขา/ผู้ใช้เพิ่มขึ้นอีก
   ทางแก้คือย้ายงานที่เรียกถี่ที่สุด (เช่น `getStockItems`) ออกจาก GAS ไปที่ office-server หรือฐานข้อมูลจริง
