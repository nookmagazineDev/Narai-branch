# เมนูครัวกลาง — ฝั่ง office-server

## สรุป

`office-server/kitchen.js` เก็บตรรกะ SQL ของเมนูครัวกลางทั้งหมด ซึ่งเป็น**เมนูของแอป
[storefct](https://github.com/nookmagazineDev/narai-storefct)** ไม่ใช่ของแอปนี้ — แต่โค้ดต้องอยู่
ที่นี่ด้วยเหตุผลเดียวกับงานสโตร์: Vercel ต่อ SQL Server ตรงไม่ได้ เพราะไฟร์วอลล์ที่ออฟฟิศเปิด
พอร์ต 1433 ให้เฉพาะ IP ในไทย

```
เบราว์เซอร์ ──► /api/kitchen (storefct บน Vercel)
            ──► office-server :8787/schedule (เครื่องที่ออฟฟิศ)
            ──► SQL Server / InventoryNarai
```

แอปนี้ (Narai-branch) ไม่มีหน้าไหนเรียก action ชุดนี้เลย สิ่งที่เปลี่ยนในฝั่ง Vercel ของ repo นี้
มีแค่รายชื่อ action อ่านอย่างเดียวใน `api/schedule.js` เพื่อให้ตัวส่งต่อยิงซ้ำได้เมื่อเน็ตสะดุด

## ครัวกลางคือ "สาขา" หนึ่งในระบบเดิม

ตั้งรหัสที่ env `KITCHEN_BRANCH` ผลที่ตามมาซึ่งตั้งใจให้เป็นแบบนี้:

- ใช้ `dbo.stock_item` ชุดเดียวกับสาขา ไม่มี master สินค้าซ้อน
- รับวัตถุดิบผ่าน `kitchen_material_receipt` (ครัวกรอกเองตอนของมาถึง) ไม่ใช่ผ่านใบเบิก
  เหมือนสาขา เพราะครัวกลาง**ไม่ใช่ outlet ในระบบ POS** จึงไม่มีใบเบิกของตัวเองใน
  `myfbdata.orderd` ให้ไหลเข้า `store_receiving`
- นับสต๊อกผ่านหน้านับสต๊อกเดิม ลง `dbo.stock_count` เหมือนทุกสาขา

ไฟล์นี้จึงเก็บเฉพาะสิ่งที่ระบบเดิมไม่มี คือ **สูตร** กับ **การผลิต**

## ยอดคงเหลือคำนวณสด ไม่เก็บเป็นตัวเลขนิ่ง

```
คงเหลือ = ยอดนับล่าสุด + รับเข้า - เบิกไปใช้ + ผลิตได้   (นับจากหลังวันที่นับล่าสุด)

"รับเข้า" = kitchen_material_receipt + store_receiving ของสาขาที่ชื่อตรงกับ KITCHEN_BRANCH
(ตัวหลังเผื่อวันหนึ่งครัวถูกเพิ่มเป็นสาขาจริง จะได้ไม่ต้องย้ายข้อมูล)
```

ตัวเลขที่เก็บนิ่งไว้จะเพี้ยนทันทีที่มีใครลืมบันทึกอะไรสักอย่าง แล้วไม่มีทางรู้ว่าเพี้ยนตั้งแต่เมื่อไหร่
ตัวตั้งจึงเป็นการนับจริง และการนับรอบใหม่ล้างความคลาดเคลื่อนสะสมให้เองโดยอัตโนมัติ

เส้นแบ่งเป็น *วันที่* ไม่ใช่ *เวลา* เพราะใบรับของกับใบเบิกวัตถุดิบเก็บแค่วันที่ — กติกาเดียวกับที่
หน้าสต๊อกสาขาใช้อยู่

## ตาราง

สคีมาอยู่ที่ `docs/schema-kitchen-sqlserver.sql` ของ repo **storefct** (อยู่ที่นั่นเพราะเป็นเมนูของ
แอปนั้น) ต้องรันบน `InventoryNarai` ก่อนเปิดใช้

| ตาราง | เก็บอะไร |
|---|---|
| `kitchen_recipe` + `kitchen_recipe_item` | สูตร: ผลิตหนึ่งชุดได้เท่าไหร่ ใช้วัตถุดิบอะไรบ้าง |
| `kitchen_production_plan` | แผนประจำรอบ (รายวัน/รายสัปดาห์) |
| `kitchen_production_order` | คำสั่งผลิต |
| `kitchen_production_run` | บันทึกการผลิตจริง ทีละครั้ง |
| `kitchen_material_issue` | ใบเบิกวัตถุดิบออกไปใช้ผลิต |
| `kitchen_material_receipt` | ใบรับวัตถุดิบเข้าครัว |

## จุดที่ต้องระวังเวลาแก้ไฟล์นี้

- **`runSql` กับ `run` คืนคนละอย่าง** — `queryRead` คืน recordset เป็น array ส่วน `run` ใน
  `withTransaction` คืน result object ต้องอ่าน `.recordset` เอง หน้าตาเรียกเหมือนกันจนพลาดง่าย
  (เป็นกับดักเดียวกับที่เคยเจอใน `storework.js`)
- **`deleteKitchenRecipe` ไม่ใช้ `OUTPUT`** ต่างจาก action ลบตัวอื่นในไฟล์นี้ เพราะ
  `kitchen_recipe` มี FK แบบ `ON DELETE CASCADE` ผูกอยู่ ซึ่ง SQL Server จำกัดการใช้ `OUTPUT` ไว้
  — อ่านชื่อก่อนแล้วค่อยลบแทน
- **คำนวณวันในสัปดาห์จากสตริงวันที่ตรงๆ** ไม่ผ่าน `new Date(str)` ซึ่งตีความเป็น UTC แล้วเพี้ยน
  ไปหนึ่งวันสำหรับเขตเวลาไทย
- **`saveProductionRun` ไม่เชื่อสินค้าที่หน้าเว็บส่งมาเมื่อผูกกับคำสั่งผลิต** — ดึงจากใบสั่งแทน
  ไม่งั้นบันทึกผลิตสินค้า A ใส่ใบสั่งสินค้า B ได้โดยไม่มีอะไรทัก
- **`produced_qty` คิดใหม่จากผลรวมทุกครั้ง ไม่บวกสะสม** เพราะถ้าเคยลบ run ทิ้ง การบวกสะสม
  จะค้างยอดเก่าไว้ตลอดกาล

## ก่อนเปิดใช้

1. รัน `docs/schema-kitchen-sqlserver.sql` ของ repo storefct บน `InventoryNarai`
2. ตั้ง `KITCHEN_BRANCH=<รหัสสาขาครัวกลาง>` ใน `.env` ของ office-server แล้วรีสตาร์ต
   `NaraiUsageAPI`

   ตอนนี้ครัวกลางยังไม่ใช่สาขาในระบบ (ตรวจจาก `stock_count` แล้ว มีแต่รหัสร้าน 17 ตัว) ค่านี้จึง
   ยังไม่มีข้อมูลให้จับคู่ ตั้งเป็น `kitchen` ไว้ก่อนได้ — มีผลแค่คอลัมน์ "นับล่าสุด" กับส่วนของ
   "รับเข้า" ที่มาจาก `store_receiving` ซึ่งจะเป็น 0 จนกว่าครัวจะเป็นสาขาจริง ระหว่างนี้คงเหลือ
   คิดจาก `kitchen_material_receipt` ล้วนๆ ซึ่งถูกต้องอยู่แล้ว
3. `git pull` ที่ `D:\Narai-branch-main` แล้วรีสตาร์ตเซอร์วิส
